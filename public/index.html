Spring AI 实战踩坑：解决 Redis 向量索引丢失与 API 限流双重难题

一、背景

最近在做一个 CityWalk 路线规划的 RAG 项目：用 Spring AI + Redis Stack（RediSearch）做向量库，Embedding 走硅基流动的 BAAI/bge-m3（免费额度、1024 维），LLM 用 DeepSeek。整体链路是：

MySQL POI 数据 → 向量化 → RedisVectorStore（poi-index）→ 相似度召回 → LLM 生成路线

技术栈：Spring Boot 3.3.5 / Spring AI 1.0.0-M6 / Java 17 / Jedis 5.1.0。

在联调阶段，我连续踩了两个看似不相干、实则都指向同一个根因的坑：poi-index: no such index 和 Connection reset（API 限流）。这篇复盘把它们的排查过程和根治方案一起写清楚。

二、问题一：poi-index: no such index —— 索引莫名消失

现象

初始化向量库的接口调用正常返回，但随后一调检索接口（similaritySearch），就抛：

redis.clients.jedis.exceptions.JedisDataException: poi-index: no such index
诡异的是，poi-index 明明是我在启动时通过 initializeSchema(true) 建好的。

排查过程
用 redis-cli 执行 FT._LIST，发现 poi-index 真的没了。

回想我本地调试时刚执行过一次 flushdb 清缓存 —— 而 RediSearch 的索引本质上是 Redis 里的特殊 key，flushdb 会把它一并清掉。

索引没了，但服务没重启，也没有任何地方去重建它，于是后续所有 FT.SEARCH 直接命中 "no such index"。

根因
关键在于 RedisVectorStore 的建索引逻辑：索引创建动作只发生在 afterPropertiesSet() 里，而 Spring 容器只在 Bean 初始化时调用一次。更关键的是，这个方法内部是幂等的——它会先 FT._LIST 检查索引是否已存在，存在就直接返回，不再重建：

java
// RedisVectorStore 内部伪逻辑（简化）
public void afterPropertiesSet() {
    if (indexExists(indexName)) {   // 已存在 → 直接返回
        return;
    }
    createIndex();                  // 不存在 → 建索引
}
所以问题变成了：启动时索引建好了 → 运行期被 flushdb 清掉 → 但 afterPropertiesSet 已经不会再跑 → 索引永久缺失。这正是文档里那句"删索引后必须重启项目"的由来。

解决方案
最优雅的做法不是重启，而是在需要重建索引的入口处，手动再触发一次 afterPropertiesSet()。因为它幂等，重复调用是安全的：

java
@Override
public int initPoiVectors() {
    // 0. 确保索引存在：flushdb 会把 poi-index 一起清掉，需重建。
    //    afterPropertiesSet 内部会先 ftList 检查，索引已存在则直接返回，幂等。
    if (vectorStore instanceof RedisVectorStore redisVectorStore) {
        redisVectorStore.afterPropertiesSet();
    } else {
        log.warn("VectorStore 不是 RedisVectorStore 实例，无法自动重建索引（实际类型：{}）", 
                  vectorStore.getClass().getName());
    }

    // 1. 从 MySQL 读所有 POI，拼检索文本 + 元数据
    // 2. 批量 vectorStore.add(documents)
    // ...
}
这里的 instanceof RedisVectorStore 防御性判断是必要的——因为容器里注入的是 VectorStore 接口，如果未来换成别的实现，这段代码不能误调。

附带一个相关坑
RedisVectorStore 底层依赖 RediSearch，而 RediSearch 的索引只能建在 database 0。如果你的 Jedis 连接指到了别的 db（比如 /1），索引根本建不起来，且报错信息极其隐晦。这一点我在排查时也确认过：连接必须落在 db 0。

三、问题二：Connection reset —— 硅基流动 API 限流
现象
重建索引后，initPoiVectors 又报了一个新错：java.net.SocketException: Connection reset，或者偶发地报 EmbeddingList 解析错误。而同样的请求，Postman 直连硅基流动却是通的。

排查过程
Postman 直连硅基流动 → 成功返回 1024 维向量，说明外部服务本身正常。

观察报错时机：每次都发生在请求刚发出不久、还没拿到业务响应时。

抓包/加日志看请求次数，发现了一个关键异常：我只是想初始化向量，但代码却多发出了一次额外的 embedding 请求。

硅基流动的免费模型有严格的 RPM（每分钟请求数）限制，多出来的这次"计划外请求"成了压垮骆驼的最后一根稻草，直接把后续真正的 embedding 请求给限流 reset 了。

根因：Spring AI 会"偷发"探测请求
罪魁祸首是 OpenAiEmbeddingModel 的一个隐藏行为：当框架不知道向量维度时，它会发一次真实的 embedding 探测请求（用一个测试文本，比如 "Hello World"），用返回向量的长度来推断 dimensions()。

也就是说，dimensions() 这个看似无副作用的 getter，默认实现里居然藏了一次真实的网络调用：

java
// Spring AI 默认行为（简化示意）
public int dimensions() {
    // 用一次真实 embed 探测来推断维度
    return this.embed(List.of("Hello World")).get(0).length;
}
在免费额度 + 严格限流的场景下，这次"多余"的探测请求就可能触发限流，进而污染后续请求。

解决方案：重写 dimensions()
bge-m3 固定 1024 维，维度是已知的、写在配置里的。既然如此，就别让框架去"猜"，直接 override：

java
@Bean
public EmbeddingModel embeddingModel() {
    OpenAiApi openAiApi = OpenAiApi.builder()
            .baseUrl(baseUrl)
            .apiKey(apiKey)
            .build();

    OpenAiEmbeddingOptions options = OpenAiEmbeddingOptions.builder()
            .model(model)   // BAAI/bge-m3
            .build();

    // bge-m3 固定 1024 维。覆盖 dimensions() 直接返回，
    // 避免 Spring AI 为探测维度额外发起一次 embed("Hello World") 调用。
    return new OpenAiEmbeddingModel(openAiApi, MetadataMode.EMBED, options) {
        @Override
        public int dimensions() {
            return EmbeddingConfig.this.embeddingDimension;   // 1024
        }
    };
}
改完之后，初始化向量时不再有那次计划外的探测请求，限流问题随之消失。

四、工程反思
框架的"智能"是有代价的。Spring AI 帮你自动建索引、自动探测维度，看起来很贴心，但在"免费额度、严格限流"这类受限环境下，这些隐式行为会从"便利"变成"事故源"。越"省事"的框架，越要读懂它背后到底帮你做了什么。

幂等设计救了我。正因为 afterPropertiesSet() 内部是"先检查、再创建"的幂等语义，我才敢在业务入口重复调用它来重建索引，而不用担心破坏已有数据。写基础设施代码时，把"可重复执行"当成第一原则，能省掉大量排障成本。

"Postman 通、Java 不通"永远先怀疑中间层。硅基流动本身没问题，问题出在 Spring AI 多发了一次请求。排查这类问题，别先怀疑外部服务，先数清楚"你到底发出了几次请求、请求体是什么"。

向量维度这种元信息，显式配置优于运行时探测。探测维度本质是框架在为"懒"买单——多一次网络往返、多一次限流风险，还引入不确定性。当维度是已知常量时，直接告诉它。

五、总结
两个报错，一个指向索引，一个指向限流，看似无关，本质都源于框架的隐式行为与运行环境的约束不匹配：

报错	根因	解法
poi-index: no such index	索引只建一次，flushdb 后不重建	入口处手动调用幂等的 afterPropertiesSet()
Connection reset	dimensions() 默认发探测请求触发限流	重写 dimensions() 直接返回已知维度
写框架代码的最高境界，不是"能用"，而是"知道它每一步在干什么"。这次踩坑，值。

RAG 工程化落地：如何解决跨城市数据污染与检索幻觉

一、背景

CityWalk 项目要做一个”按城市生成游玩路线”的 RAG 功能：用户输入城市 + 主题 + 时长，系统检索相关 POI，再交给 LLM 编排成路线。

POI 数据覆盖全国多城市，向量库（Redis Stack）里存的是所有城市混在一起的 POI 向量，总共有几万条。最初的实现非常”标准”——直接把用户 query 丢进向量库做相似度检索，取 Top-K 喂给 LLM。

结果上线前联调，出事了。

二、问题：佛山搜出苏州和北京的景点

用户选了佛山，主题”美食”，出来的路线里却赫然出现了苏州的拙政园、北京的老字号。

乍一看是 LLM “胡编乱造”（幻觉），但顺着链路查下去，发现 LLM 其实很无辜——它是照着被污染过的召回结果来编路线的。真正的问题在召回环节：向量检索把跨城市的 POI 召回来了。

三、根因一：向量库全量检索的天生缺陷

向量检索的本质是语义相似度排序，它对”城市”这个概念毫无感知。当我把全量 POI 混在一个索引里，然后执行：

List<Document> docs = vectorStore.similaritySearch(
        SearchRequest.builder()
                .query(query)   // "美食 轻松 3小时"
                .topK(30)
                .build()
);
它返回的是整个向量空间里和 query 最相似的前 30 个 POI，完全不管这些 POI 属于哪个城市。而"跨城市的同类 POI"语义往往更相似——"佛山的茶楼"和"苏州的茶楼"在向量空间里可能比"佛山的茶楼"和"佛山的博物馆"更近。

这就引出一个核心认知：

向量检索是"软过滤"——它只能告诉你"谁更像"，不能告诉你"谁符合条件"。精确的、确定性的约束（比如 cityId = 佛山），永远不该指望向量库来保证。

四、根因二：Metadata 在链路里"丢了"
看到这里，有经验的同学可能会说：那我在写入时把 cityId 塞进 metadata，检索时按 metadata 过滤不就行了？

我也这么想的。写入时确实带了元数据：

java
Map<String, Object> metadata = new HashMap<>();
metadata.put("poiId", poi.getId());
metadata.put("name", poi.getName());
metadata.put("cityId", poi.getCityId());
Document doc = new Document(text, metadata);
但一检索，日志里打出来的 metadata 却是空的：文档 [0] metadata: {}。

排查后确认：这是 Spring AI 1.0.0-M6 里 RedisVectorStore 的已知行为——similaritySearch 返回的 Document 不携带 metadata（写入时存进去了，读取时没回填）。依赖 metadata 做二次过滤这条路，在这个版本上直接走不通。

这让我学到一个教训：任何"你以为会跟着数据一起回来的字段"，都要在真实的读写链路上验证一次，而不是想当然。

兜底：把 poiId 埋进 text，用正则提取
metadata 拿不到，那就退而求其次——把关键 ID 直接拼进检索文本（text）里。因为 text 是一定会返回的：

java
// 写入时：把 poiId 拼进文本开头
String text = "poiId:" + poi.getId() + " " +
        (poi.getName() != null ? poi.getName() : "") + " " +
        (poi.getCategory() != null ? poi.getCategory() : "") + " " +
        (poi.getAddress() != null ? poi.getAddress() : "");

// 召回后：用正则从 text 里把 poiId 抠出来
List<Long> poiIds = docs.stream()
        .map(d -> extractPoiId(d.getText()))   // 正则 "poiId:(\\d+)"
        .filter(Objects::nonNull)
        .collect(Collectors.toList());
这个 hack 不优雅，但在"metadata 不可用"的现实约束下，它稳稳地保住了 ID 这条命脉。

五、方案：向量召回 + MySQL 结构化反查过滤
两条根因拼在一起，其实已经指明了方向。既然向量库既不能过滤城市、又给不了 metadata，那就让向量库只干它擅长的事，把"精确过滤"交给数据库：

text
[用户 query] ──▶ [向量库宽召回 Top30] ──▶ [MySQL 反查完整POI] ──▶ [LLM 编排]
                  (软召回，允许脏)          (selectBatchIds + 硬过滤)
核心代码：

java
// 1. 宽召回：向量库只负责"可能相关"，topK 故意放大到 30
List<Document> docs = vectorStore.similaritySearch(
        SearchRequest.builder().query(query).topK(30).build());

// 2. 从 text 提取 poiId（metadata 不可用，正则兜底）
List<Long> poiIds = docs.stream()
        .map(d -> extractPoiId(d.getText()))
        .filter(Objects::nonNull)
        .collect(Collectors.toList());

// 3. MySQL 结构化反查：批量拿完整字段
List<Poi> pois = poiMapper.selectBatchIds(poiIds);

// 4. 城市硬过滤：这才是"确定性约束"的正确落点
if (request.getCityId() != null) {
    pois = pois.stream()
            .filter(p -> p.getCityId() != null && p.getCityId().equals(request.getCityId()))
            .limit(10)
            .collect(Collectors.toList());
}
这个架构的每一层各司其职：

向量库做"召回"：牺牲一点精度，换取高召回率（topK 放大到 30），允许跨城市的脏数据先进来。

MySQL 做"精排前的硬过滤"：用结构化字段 cityId 做精确过滤，limit(10) 收窄候选集。这一步是"确定性约束"的正确落点——数据库的 WHERE city_id = ? 是硬保证，和语义相似度无关。

LLM 做"生成"：它拿到的 POI 列表已经是"同城 + 结构化可信"的，编造幻觉的概率大幅下降。

本质上，这就是把搜索引擎"召回—粗排—精排"的思想搬到了 RAG 里：向量召回负责"可能相关"，结构化过滤负责"确定相关"。

六、工程反思
检索幻觉的根因常常不在 LLM，而在召回源。 看到 LLM "乱编"，先查它拿到的上下文是不是已经被污染了。给 LLM 喂干净、可信的上下文，比事后调 prompt 有用得多。

把"软约束"和"硬约束"分开。 语义相似度是软约束（多高都不算绝对），cityId 是硬约束（非黑即白）。软约束交给向量库，硬约束交给数据库，二者用 ID 串起来。别让向量库去做它不擅长的事。

框架的已知 bug/局限要主动规避，而不是硬扛。 metadata 不返回是 M6 的已知行为，与其等它修复，不如立刻切换成"text 埋 ID + 正则提取"的兜底方案，把风险控制在当下能落地的范围内。

ID 是贯穿整个检索链路的生命线。 只要 ID 不丢，向量召回结果就可以随时回到 MySQL 反查出权威数据。这也是我坚持把 poiId 埋进 text 的原因——给链路留一条随时能"落地"的后路。

七、总结
跨城市数据污染这个问题的解决，靠的不是某个炫技的算法，而是认清每一层能力边界，并把它们正确地组合起来：

向量库：软召回，允许脏，topK 放大。

正则 + text 埋点：在 metadata 不可用时的 ID 兜底。

MySQL：硬过滤 + 权威数据反查。

RAG 工程化落地的关键，从来不是"能不能跑通"，而是当输入不可控、框架有坑时，你的链路是否依然可控。

MyBatis-Plus 实战：多表联查 N+1 优化与点赞并发防重

一、背景

项目里的社区模块，帖子列表要联查用户信息、关联 POI，还要带上每条帖子的点赞数、评论数、当前用户是否已点赞。典型的多表联查 + 聚合统计场景，也是 N+1 问题和并发幂等问题的重灾区。

技术栈：Spring Boot 3.3.5 / MyBatis-Plus 3.5.7 / MySQL 8 / InnoDB。

二、N+1 问题与 selectBatchIds 优化

第一版：循环里逐条查

最初实现很”直白”——遍历帖子列表，每条帖子单独去查它的作者、POI：

for (Post p : posts) {
    User user = userMapper.selectById(p.getUserId());   // 第 1 次 SQL
    Poi poi = poiMapper.selectById(p.getPoiId());       // 第 2 次 SQL
    // ... 每条帖子 2 次查询
}
分页 size=10 时，一次列表请求要发 1 + 10 × 2 = 21 次 SQL；size 再大一点，SQL 数量线性爆炸。这就是经典的 N+1 问题：1 次主查询 + N 次关联查询。

N+1 的危害不只是"查询次数多"：

网络往返开销：每次 SQL 都是一次 DB 往返，N 越大延迟越高；

数据库压力：连接池被大量琐碎查询占满，影响整体吞吐；

隐性放大：当 N 从 10 涨到 100，问题会悄无声息地恶化，而不是线性可感的。

优化：selectBatchIds 批量查，一次搞定
关联数据的查询有一个共同特征：它只需要 WHERE id IN (...)。既然如此，就先把所有需要的 ID 收集成一个集合，批量查一次：

java
private List<PostVO> toVos(List<Post> posts) {
    // 收集所有帖子涉及的用户 ID，一次批量查
    Set<Long> userIds = posts.stream().map(Post::getUserId).collect(Collectors.toSet());
    Map<Long, User> users = userMapper.selectBatchIds(userIds)
            .stream().collect(Collectors.toMap(User::getId, Function.identity()));

    // 收集所有帖子涉及的 POI ID，一次批量查
    Set<Long> poiIds = posts.stream().map(Post::getPoiId)
            .filter(Objects::nonNull).collect(Collectors.toSet());
    Map<Long, Poi> pois = poiIds.isEmpty() ? Collections.emptyMap()
            : poiMapper.selectBatchIds(poiIds).stream()
                    .collect(Collectors.toMap(Poi::getId, Function.identity()));

    // 组装 VO 时，直接从内存 Map 里取，不再发 SQL
    for (Post p : posts) {
        PostVO vo = new PostVO();
        fillAuthor(vo, users.get(p.getUserId()));
        if (p.getPoiId() != null && pois.get(p.getPoiId()) != null) {
            vo.setPoiName(pois.get(p.getPoiId()).getName());
        }
        // ...
    }
}
selectBatchIds 底层就是一条 SELECT * FROM user WHERE id IN (?, ?, ...)。用户和 POI 的查询从 2N 次降到了 2 次，与分页大小彻底解耦。

还能继续优化：点赞数/评论数的聚合
但注意，上面的代码里，点赞数、评论数仍然在循环里逐条 selectCount：

java
vo.setLikeCount(postLikeMapper.selectCount(
        new LambdaQueryWrapper<PostLike>().eq(PostLike::getPostId, p.getId())).intValue());
vo.setCommentCount(postCommentMapper.selectCount(
        new LambdaQueryWrapper<PostComment>().eq(PostComment::getPostId, p.getId())).intValue());
这又是 2N 次查询。它的正确解法不是 selectBatchIds，而是用 GROUP BY 一次性聚合：

sql
SELECT post_id, COUNT(*) AS cnt
FROM post_like
WHERE post_id IN (...)
GROUP BY post_id;
（MyBatis-Plus 里用自定义 mapper 方法，或者 selectMaps + in + groupBy 实现。）这样 N 条帖子的点赞数/评论数，从 2N 次降到 2 次聚合查询。核心思路是一致的：把"逐条"变成"批量/聚合"。

三、点赞并发防重：先查后插的竞态窗口
点赞是典型的"幂等"需求——同一个用户对同一个帖子，只能点赞一次。

最初的实现是业务层先查后插：

java
@Override
@Transactional
public void like(Long postId) {
    Long userId = UserContext.getUserId();

    // 先查：点过就直接返回
    Long count = postLikeMapper.selectCount(
            new LambdaQueryWrapper<PostLike>()
                    .eq(PostLike::getUserId, userId)
                    .eq(PostLike::getPostId, postId));
    if (count != null && count > 0) {
        return; // 已点过，幂等
    }

    // 后插：没点过就插入一条记录
    PostLike like = new PostLike();
    like.setUserId(userId);
    like.setPostId(postId);
    like.setCreatedAt(LocalDateTime.now());
    postLikeMapper.insert(like);
}
这段代码单线程下完全正确，但并发下有一个经典的竞态窗口（check-then-act）：

text
时间线          请求A                    请求B
─────────────────────────────────────────────────
  t1          selectCount → 0
  t2                                   selectCount → 0
  t3          insert 成功
  t4                                   insert 成功  ← 重复点赞！
两个请求几乎同时通过了 selectCount 检查，都拿到了"0"，于是都执行了 insert，产生两条重复的点赞记录。业务层的 if 判断，挡不住并发。

这也说明一个关键认知："先查后插"里的那次"查"，在并发语义下只能当优化手段，不能当正确性保证。

四、数据库唯一键 + 捕获 DuplicateKeyException 兜底
要根治，就必须把"唯一性"下沉到数据库约束这个唯一可靠的地方。表结构上给 (user_id, post_id) 加唯一键：

sql
CREATE TABLE post_like (
    id         BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id    BIGINT NOT NULL,
    post_id    BIGINT NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_user_post (user_id, post_id)   -- 关键：唯一约束
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='帖子点赞';
有了唯一键，并发场景下 InnoDB 只会让一个 insert 成功，另一个必然抛 DuplicateKeyException。业务代码改成"直接插 + 捕获异常兜底"：

java
@Override
@Transactional
public void like(Long postId) {
    Long userId = UserContext.getUserId();

    PostLike like = new PostLike();
    like.setUserId(userId);
    like.setPostId(postId);
    like.setCreatedAt(LocalDateTime.now());

    try {
        postLikeMapper.insert(like);
    } catch (DuplicateKeyException e) {
        // 唯一键冲突 = 已经点过赞，幂等返回
        log.info("重复点赞，幂等跳过 userId={}, postId={}", userId, postId);
    }
}
几个关键点：

唯一键是"最终兜底"，不是"优化"。 并发下它的正确性由 InnoDB 的行锁/唯一索引保证，与业务代码的时序无关。

异常要在事务边界内吃掉。 DuplicateKeyException（Spring 对 MySQL 1062 错误码的翻译，是 DataIntegrityViolationException 的子类）被方法内部 catch 后，不会传播到事务切面，事务不会被误标成 rollback-only，返回即可。

可以保留"先查"作为快路径。 在大多数请求是"重复点赞"的高频场景下，先查可以省掉一次注定失败的 insert 和异常栈开销。但要记住：那次"查"的结果只是"建议"，真正的正确性始终由唯一键保证。

同样的思路可以直接复用到收藏（favorite）——给 (user_id, post_id) 建唯一键，收藏与取消收藏都走"插入 + 捕获冲突"或"删除 + 判断影响行数"的模式。

顺带一提：unlike 的幂等
取消点赞天然幂等（删不存在的记录也返回成功），所以直接 delete 即可，无需额外处理：

java
postLikeMapper.delete(
        new LambdaQueryWrapper<PostLike>()
                .eq(PostLike::getUserId, userId)
                .eq(PostLike::getPostId, postId));
五、工程反思
业务层的 if 挡不住并发，数据库约束才是幂等的底线。 check-then-act 的竞态是分布式系统的经典问题，单靠"先查"无法根治。任何"唯一"语义，都应该最终落成数据库的唯一索引。

性能优化和正确性保证要分开思考。 selectBatchIds 是性能优化（减少 SQL 次数），唯一键是正确性保证（保证幂等）。两者都很重要，但别混淆它们的职责。

异常也是正常的控制流。 很多人对"用异常做业务分支"有心理障碍，但 DuplicateKeyException 兜底恰恰是并发幂等里最简洁、最可靠的标准做法——它把"冲突"这个并发结果，用数据库的语言明确地抛了出来。

识别"逐条循环"这个坏味道。 凡是看到 for 循环里出现 selectById / selectCount，先问一句：能不能用 selectBatchIds 或 GROUP BY 把它变成批量/聚合？这几乎是后端性能优化的第一直觉。

六、总结
这一篇里解决的两个问题，恰好对应后端开发的两条基本功：

问题	根因	解法
列表查询慢	N+1：循环逐条查关联数据	selectBatchIds 批量查 + GROUP BY 聚合
并发重复点赞	先查后插的竞态窗口	数据库唯一键 + 捕获 DuplicateKeyException
前者告诉我们：把"逐条"变成"批量"。
后者告诉我们：把"正确性"交给数据库。

这两条，值得写进肌肉记忆。
